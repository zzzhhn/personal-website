## Product thesis

Recommendation systems decide what a listener may like. Automix systems decide how two already-chosen tracks should overlap. The missing product layer is the decision between them: which next track is musically compatible enough to mix, and how can that recommendation be explained?

Hepai was built for the Tencent Music AI Hackathon around that gap. It treats mixability as a ranking and sequencing problem, then connects the result to a browser-native transition engine. The concept is relevant to a QQ Music-style listening experience, but the current product is an independent case study rather than an implemented QQ Music integration.

## What I owned

- **Product framing:** defined the value proposition around mix-ready continuity, not another generic similarity recommender.
- **Music intelligence:** built feature extraction and scoring across tempo, harmonic key, energy, style, spectral character, and structural cues.
- **Playlist strategy:** designed explainable seed recommendations and multi-track sequencing with mode-specific weights, compatibility gates, and repetition controls.
- **Listening experience:** delivered a static Web Audio demo with dual decks, cue-aware transitions, equal-power crossfades, and a DJ-style bass-swap mode.

## From audio analysis to next-track decision

The Python pipeline uses `librosa` to estimate BPM, musical key mapped to the Camelot wheel, energy, onset and spectral features, and candidate transition points. Compatibility is not represented by one opaque similarity score. Harmonic distance, tempo distance, energy continuity, and style signals are weighted by listening mode, making the recommendation traceable to musical attributes.

For a seed track, Hepai ranks the strongest candidates. For a longer set, a greedy sequencer chooses the next compatible track while applying style gates and an artist-run penalty. Different modes alter the energy arc and tolerance for variety, allowing the same catalogue to support steady listening, running, driving, or a more expressive DJ sequence.

## Browser-native delivery

The public demo ports recommendation, sequencing, and mix-plan logic from Python to JavaScript. A cross-language golden harness currently covers 42 cases so the browser does not silently diverge from the reference implementation. Playback uses two Web Audio decks with equal-power fades at precomputed cues; DJ mode adds a BiquadFilter bass exchange without requiring server-side rendering.

The static bundle includes 10 Kevin MacLeod tracks under CC BY 4.0 and explicitly excludes private or QQ Music audio assets. That licensing boundary is part of the product design, not an afterthought.

## Current scope

Hepai is a completed hackathon case study. It demonstrates music recommendation, playlist optimization, Music Information Retrieval (MIR), and browser audio delivery, but does not claim access to QQ Music APIs, a production catalogue, or measured listener retention.

## 产品命题

推荐系统回答“用户可能喜欢什么”，Automix 回答“已经选好的两首歌如何重叠”。两者之间仍缺少关键一层：下一首究竟应该选谁，它为什么具备可混音性？

合拍围绕这一缺口参加腾讯音乐 AI Hackathon。它先把可混音性建模为排序与编排问题，再把结果连接到浏览器原生转场引擎。该概念可以嵌入 QQ 音乐式的连续收听体验，但当前交付是独立产品案例，并非已经完成的 QQ 音乐接口集成。

## 我的核心职责

- **产品定义：** 将价值主张锚定在“可混音的连续性”，而不是再做一套泛化相似度推荐。
- **音乐智能：** 构建覆盖 Tempo、和声调性、能量、风格、频谱特征与结构 Cue 的提取和评分体系。
- **播放列表策略：** 设计可解释的种子推荐与多曲编排，引入模式化权重、兼容门控与重复控制。
- **收听体验：** 交付静态 Web Audio Demo，以双 Deck、Cue-aware 转场、Equal-power Crossfade 与 DJ 风格 Bass Swap 完成播放。

## 从音频分析到下一首决策

Python Pipeline 使用 `librosa` 估计 BPM、映射至 Camelot Wheel 的 Musical Key、能量、Onset、频谱特征与候选转场点。系统不会把全部判断压缩成无法解释的相似度分数，而是按聆听模式组合和声距离、速度距离、能量连续性与风格信号，让每次推荐都能回到具体音乐属性。

面对种子曲目，合拍会对最具兼容性的候选进行排序；面对更长的播放序列，贪心 Sequencer 会在风格门控与连续歌手惩罚下选择下一首。不同模式调整能量走向与多样性容忍度，使同一曲库可以适配稳定收听、跑步、驾驶或更具张力的 DJ Sequence。

## 浏览器原生交付

公开 Demo 将推荐、编排与 Mix Plan 从 Python 移植到 JavaScript，并通过当前 42 个跨语言 Golden Case 防止浏览器实现与参考算法静默偏离。播放链路由两个 Web Audio Deck 构成，在预计算 Cue Point 执行 Equal-power Fade；DJ 模式则借助 BiquadFilter 完成低频交换，无需服务端渲染。

静态包只包含 10 首采用 CC BY 4.0 授权的 Kevin MacLeod 曲目，并显式排除私有或 QQ 音乐音频资产。版权边界在这里属于产品设计的一部分，而不是上线前的补救措施。

## 当前边界

合拍是已经完成的 Hackathon 产品案例，呈现音乐推荐、Playlist Optimization、Music Information Retrieval（MIR）与浏览器音频交付能力；它不宣称已经接入 QQ 音乐 API、拥有生产曲库或取得经过验证的留存数据。
