# 3D 世界：Agent 检查与玩家体验分工

2026-11-15。按 Bobby 最新反馈调整：减少低收益的 computer use 漫游，把可重复的技术检查交给 Agent，把手感、探索与审美的最终判断交给玩家。本文是项目执行约定，不声称下面所有检查已自动化。

## 1. Agent 必须承担的工作

| 变动 | 首选检查 | 能证明什么／不能证明什么 |
| --- | --- | --- |
| 地形、地基、道路、楼梯 | 用生产真实三角面采样完整承重足迹；对人物胶囊做净空及路线扫掠；复查出入口和救援点 | 可发现悬空、埋入与通路阻塞。AABB 或中心点高度不能替代完整足迹；桥梁须检查桥墩，不能把桥面强行贴地。 |
| 角色与交互 | 真实骨骼接触误差、固定物理步进、状态转换与取消路径；暂停、切场景、重复输入、慢加载 | 可查到“出现提示却够不到”“物理地面尚未挂载就下落”等错误；不能证明动作好看或手感舒服。 |
| 模型与材质 | 对新增／变更 GLB 做格式与引用检查，查法线、UV、缩放、色彩空间、纹理槽、透明深度、运行时材质适配；按资产类型比较面数与绘制批次 | glTF Validator 能检查规范和数据，不能证明资产质感。运行时材质仍需有代表性的实际图像。 |
| 性能 | 先查每帧分配、React／store 高频通知、重复材质与几何、额外渲染 pass、不可见区更新、音频与监听器清理；有运行条件再抓短 trace 归因 | 不凭下载文件大小推断显存，不凭平均 FPS 宣称稳定，不因测试机内存压力就删材质或降清晰度。 |
| 集成与交付 | 审阅实际 diff、定向回归、类型与构建、入口及资产 HTTP、构建指纹、可回退的冻结预览 | 可证明送达了哪一版。HTTP 200 和构建通过不等于交互已体验。 |

Rapier 提供射线、形状及重叠查询，适合做真实碰撞事实检查。[Rapier 场景查询](https://rapier.rs/docs/user_guides/javascript/scene_queries/) 当前在线文档为 0.21，本项目锁定 0.19.2；实施 API 以本地包为准，不为采用文档而顺手升级物理引擎。

R3F 明确建议避免在快速循环里 setState、避免重复创建几何与材质，并使用 delta 驱动运动。[R3F performance pitfalls](https://r3f.docs.pmnd.rs/advanced/pitfalls) Three.js 的几何、材质和纹理有显式释放责任，共享资源必须按实际所有权释放。[Three.js cleanup](https://threejs.org/manual/pages/cleanup.html)

资产规范检查可采用 [Khronos glTF Validator](https://github.com/KhronosGroup/glTF-Validator)，但不能把“规范通过”写成“建模完成”。这轮没有引入新验证依赖。

## 2. 少量有目的的运行时检查

- 仅对本次变动选代表机位或交互，不每轮遍历整个世界。优先复用已有截图、用户反馈和已存在的测试入口。
- 材质／几何改变时，固定机位、时间、天气、视口、DPR 和 Balanced；必要时再查一个夜景或近景。动态水、草、粒子需要固定时间或限定比较区域，不能把随机差异误报为退化。
- 截图回归用于发现意外改变，基线必须是已认可版本；不能自动接受新图。浏览器、操作系统、硬件会影响渲染结果。[Playwright visual comparisons](https://playwright.dev/docs/test-snapshots)
- 物理无浏览器回归不能覆盖 Suspense 挂载时序、WebGL 编译和浏览器输入。风险涉及这些层时，只补一次针对性的运行检查；控制连接失败则写清缺口，交给用户定点体验，不重复连接耗费时间。
- 性能对照固定路线、质量、视口、浏览器及前后台状态，区分冷启动与热运行。记录帧时间分布及长帧次数，结合主线程、GC、编译、物理与 GPU 活动定位；不要仅靠 FPS。短 trace 按需抓取。[Chrome Performance](https://developer.chrome.com/docs/devtools/performance/reference)
- Long Animation Frames 可辅助定位超过 50 ms 的渲染更新，但不覆盖所有掉帧，也不是完整 GPU 分析；须先检测浏览器支持。[MDN LoAF](https://developer.mozilla.org/en-US/docs/Web/API/Performance_API/Long_animation_frame_timing)

## 3. 每轮交付给玩家的内容

默认 2～4 个直接入口，每个只给：操作、预期变化、最值得关注的问题。玩家不负责跑完整 QA，也不需要打开开发者工具。

反馈只需截图或文字：发生在哪、刚才做了什么、看见什么。能给入口 URL 更好，但不是前提。Agent 负责把反馈转成坐标、状态、输入序列或图像反例，补回归并检查同类问题，避免反复让用户发现同一个根因。

交付使用真实状态：技术检查通过／Agent 实景抽查通过／待玩家体验／玩家已认可。已知严重技术失败先修；技术检查通过但手感或美术待定的本地候选版可以交用户体验。保留上一冻结版，禁止把“待体验”写成“全部通过”。
