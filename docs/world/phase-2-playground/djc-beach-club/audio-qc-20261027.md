## 修前代码发现与主线修复方向

### 进行中的转场取消没有保留瞬时参数

修前 `WorldClubAudio.ts:153～157` 对 gain／filter 使用 `cancelScheduledValues(now)`。按 [Web Audio 规范](https://webaudio.github.io/web-audio-api/#dom-audioparam-cancelscheduledvalues)，取消运行中的 value curve 会移除该事件，可能立即恢复先前值而产生不连续。接着 `updateLevels()` 使用整拍发布的 `snapshot.crossfade`，该值还可能落后实际曲线近一拍。

例：0 → 1 的四拍 fade 已走 2.5 拍时，实际 gain 约 0.556／0.831，而上一整拍快照可能仍对应 0.707／0.707。此时通过滤波、Cue 等取消，旧实现不能保证连续保音。此项为源码和规范审查结论，没有伪称已实际听到 click。

主线已采纳 `cancelAndHoldAtTime(now)`，并在接管时按真实 beat 解析当前 crossfade。修前 144 行触发时把中间 mix 立即设成 1／0 是另一条边界，也已改成保留当前 gain、再短 ramp 接管。最终复核见下节；是否有可闻硬切仍需实际听感验收。

### 输出没有固定最终样本数，元数据仍是原曲信息

修前 `club-prepare-audio.py:19～23` 在 atempo 后没有固定 PCM 样本数；`WorldClubAudio.ts:55～60` 又取实际 buffer 与理论长度的较小值。若 Web Audio 与初轮 FFmpeg 同样解码，Backbay 每回环会提前约 0.0348 拍，而全局 beat 按 118 BPM 前进。原测试假 buffer 固定 120 秒，不能暴露该差异。

修前输出还继承 `TBP=120/115` 与描述完整原曲的 `iTunSMPB`。不把标签在特定浏览器中是否引起解码问题写成已确认故障。主线已增加 32 kHz 重采样后 pad／trim 到 1,041,356 帧，清掉旧元数据并重写 118 BPM；下节记录独立复测结果。

## 连续 beat、暂停与六个初轮测试

`transportOrigin` 在资源 ready 时建立；beat 依赖同一个 AudioContext 时间，不读取某 Deck 的循环位置。换 Deck、Cue 和文件回环不主动重置 origin。queued → build → landed 的 gain 事件使用同一 context 时间线；`tick()` 依托已有世界帧循环，没有新 timer。

暂停、隐藏、远离和静音使 allowed 为假，先停 source 保存 offset，再串行 suspend；恢复续播原 offset。计划与参数事件保留在同一时间坐标中，符合 context suspend 冻结时间的预期。`WorldDjcClub.tsx:14` 也只在世界运行时 tick。没有发现源码明确继续在墙钟上执行转场的路径，但本轮没有真实浏览器长暂停的音频时钟测量。

初轮执行 `node --import ./tools/world/alpha-mine-tests/register.mjs --test src/components/world/club-audio.test.mjs`，**6／6 通过**。涵盖有限生命周期、暂停／后台／距离／BFCache、pending resume 竞争、fetch 中释放与共享 ownership、等功率和连续 clock、正常转场落拍，以及 queued 取消／重入。

初轮 mock 的 AudioParam 方法为空（test:11），解码器固定返回 120 秒（15）；取消只测 queued、曲线未开始的路径（73～77）。通过结果没有排除正在 fade 时取消的跳变，也没有验证真实 MP3、Beat Grid、首拍或循环接缝。
