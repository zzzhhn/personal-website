Source reviewed at `personal-world-craft-batch5` commit `cdb31de`, compared with batch4 `2f22560`. Frozen R5 sixty-file hashes matched `build-r5-fourteen.json`; ground is baseline, not rejected R4. No product code changed by this review.

## Confirmed added work and minimal options

1. `WorldCampContent.tsx:247` defines `adaptVisual`; line280 invokes it from each Pushable frame callback. Four mounted pushables (guitar, two dumbbells, suitcase) now traverse their visual subtrees every frame. Single-material candidate meshes also allocate a temporary one-element array while applying the same opacity repeatedly. The legacy comparison uses this new traversal too, but its subtrees/material counts are smaller. A minimal option is an explicit child-ready notification/material registration and cached material list, applying transparency/depthWrite/opacity only when fade changes. Preserve late Suspense swaps and the30-second reset contract; an effect on the unchanged parent alone would miss the swap. This is definite extra CPU work, not proof it accounts for11FPS.
2. `WorldCamp.tsx:189` adds four TreeCraftPart frame callbacks, each computing the same placement-to-camera distances and LOD32m test. Cached temporaries avoid per-frame matrix/vector allocation; instance matrices upload only on LOD changes. Shared per-tree LOD decisions, squared-distance comparisons and hysteresis could remove duplicate checks and boundary thrashing if warranted. No per-frame tree reconstruction was found.
3. `WorldCampFacilityCraft.tsx:53` updates each owned material's environment intensity every frame, plus wick intensity. These are scalar writes; gate on a changed night value as a small option. Factories clone materials inside memoized construction. Original geometry/textures are borrowed; owned materials have cleanup, and the existing renderer-keyed/ref-counted PMREM cache is reused. No new private PMREM per instance or obvious accumulating target was found.
4. Frozen camp GLB has11 meshes,31 material primitives,10 materials, all10 double-sided; one is BLEND glass. The second dumbbell adds another three primitive instances. The adapter marks every rendered mesh castShadow/receiveShadow, including glass, strings and wick; old string/glow paths were not all shadow casters. Thus material/pass and caster work increases deliberately, rather than merely replacing geometry inside the old merged draw. Audit closed surfaces and shadow relevance individually; do not globally disable double-sidedness on foliage, thin sheets, open cookware or glass. A closed-surface-only FrontSide/shadow policy may be a targeted option after topology/visual review. No GPU cost is inferred from primitive totals alone.
5. Street `finishStreetFacility` runs during Builder construction; L1 returns baseline. Existing batched runtime update stays the same. Original collision builders are retained in a WeakMap and temporary collision geometries are disposed after extracting trimesh arrays. No new street per-frame builder/traversal or simultaneous old/new visual was found. Original GLBs still provide physics and fallbacks in camp; retained fallback allocations are intentional and do not establish a leak.

The wind attachment restores previous materials and disposes its copies/depth/distance materials on cleanup. Existing SceneFeedback's periodic full-scene search predates this change. This bounded source audit does not prove absence of all leaks or isolate CPU/GPU time.
